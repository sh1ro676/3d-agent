## 3. 动手前必须定的 5 个接口决策

1. **每轮动作的协议** —— 推荐 JSON 块：`{"tool": ..., "args": {...}}` 或 `{"answer": ...}`。
   不建议直接吐一行 Python：那会让「这一轮算不算 syntax 失败」与主路径的口径混起来。

2. **观察序列化的 token 预算**（⭐ 成本大头）—— `ToolResult.value` 可能是一整张物体表。
   必须定硬预算（例如 ≤400 tok/条）与显式截断声明，否则 E′ 的成本不可预测。

3. **轮次上限** —— `max_tool_turns` 必须是**显式常数**。理由与 `agents/loop.py:27-30` 对
   `max_synthesis_retries` 的说明完全相同：否则「4 轮」与「7 轮」的两次实验在报告里长得一模一样。

4. **答案如何进 `Submission`** —— E′ 的答案由我们构造，但**必须走同一套契约校验**
   （`_to_number` / `_normalize_list`），否则「弃答」判定在两条臂之间会漂移，而弃答率是硬指标。

5. **失败分类** —— 主路径的 `STATUSES` 五态不适合 E′（没有 `static_check` 这一步）。
   E′ 需要自己的枚举，例如 `parse_failed` / `turn_budget_exhausted` / `tool_error_unrecovered`。
   ⚠ `agents/loop.py:71-72` 已写明纪律：**加新状态时必须同时在 metrics 口径里交代它算不算对**，
   否则新状态会静默地既不算对也不算错。

## 4. 成本投影（基于 11 题真跑实测）

实测基线（`logs/agent_runs/`，中位）：

| 量 | 实测 |
|---|---|
| 单次 LLM 往返延迟 | **1.46 s**（n=15） |
| 单次 prompt tokens | **1549** |
| 单次 completion tokens | **300** |
| 每题工具调用数 | **2**（分布：1×5、2×4、3×4） |
| 每题 synthesize 次数 | **1** |

投影（假设每轮观察回灌 200 tok）：

| 轮数 | prompt 合计 | 相对单轮 | 墙钟 |
|---|---|---|---|
| 1（＝主路径） | 1 549 | 1.0× | 1.5 s |
| 3 | 5 247 | 3.4× | 4.4 s |
| 4 | 7 396 | 4.8× | 5.8 s |
| 6 | 12 294 | 7.9× | 8.8 s |
| 8 | 17 992 | 11.6× | 11.7 s |

**两个缓解因素，都要实测才知道成不成立**：

- **前缀缓存**：每轮的 system（工具文档占 system 的 62%）逐字节相同。若服务端缓存生效，
  turn k 的**计费**增量只是新增的后缀 ⟹ 总成本可能降到 ~1.2×。**目前测不出**（见 §5 前置 1）。
- **completion 更小**：每轮只吐一个小 JSON，不是 300-token 的完整程序 ⟹ 输出侧可能不涨反降。

## 5. 前置条件：不做，做了也读不出结论

### 前置 1 —— 账本补缓存命中字段 ✅ **已完成（2026-09-21，S0）**

`llm/adapter.py` 原先的 usage 归一化只取 `prompt_tokens` / `completion_tokens`。
而 `agents/synthesizer.py` 的 `build_messages` 注释明确承诺「工具文档进 system，逐字节稳定 →
能吃服务端前缀缓存」—— 但**账本里没有命中字段，这个承诺无法被证实**。

⟹ 不补这一项，E′ 的真实成本落在 **1.2× 与 4.8× 之间，且我们无法判断在哪**。

**已落地的读法（四个新字段）：**

| 字段 | 位置 | 怎么读 |
|---|---|---|
| `cached_tokens` | 账本 / 每次调用日志 | 命中缓存的输入 token。**`None` = 服务商没报这个字段，不是「报了 0」** |
| `cache_reported_calls` | 账本 | 回报过缓存字段的调用数。**算命中率的分母口径**：为 0 ⟹ 命中率未知 |
| `cache_hit_rate()` | 账本方法 | 没报过时返回 **`None` 而非 `0.0`** —— 「没测到」和「测了没命中」要能分开 |
| `cache_source` / `usage_keys` | 每次调用日志 | 值取自哪个字段名；以及服务商**回传的 usage 顶层键全表** |

`usage_keys` 是**一次真跑就能回答「它到底报不报缓存」**的那一列，不必再猜字段名或翻文档；
`cache_source` 从有值变成 `None`，就是「服务商改了字段名、缓存悄悄失效」的告警信号。

⚠ **口径**：`cost_cny` **刻意不套缓存折扣**（价格表只有两个数，折后价必须由服务商定义，
猜一个系数等于把估计伪装成测量）。当前口径**系统性偏高**，对预算而言是安全方向。

### 前置 2 —— 指标口径先写

E′ 与主路径**能比的只有端到端正确率**（`evaluation/metrics.py` 算的是 Omni3D 四类子指标 + Total）。

「工具选择准确率」在两条臂上**分母不同**（主路径一次选定整条序列／E′ 逐步选），
**不能放进同一张表**。

> ⚠ **此处更正一处此前的说法**：曾讲过「单轮契约让工具选择准确率可观测」，核对后**不准确**。
> 它只出现在三处 —— 注释（`agents/executor.py:101`）、方案文档（§453 与 §1213 的消融表列名）、
> 探针报告（`reports/combination_probe.md:285`）—— 而 **`evaluation/metrics.py` 里没有实现**。
> 原始材料（每次调用与完整 trace）确实在记录里，**但指标本身没写**。
> 这与 §14 那条教训同型：**文档里写了 ≠ 代码里有**。

## 6. 风险与混淆变量

1. **不是纯消融** —— E′ 的 system prompt 与主路径必然不同。要保持干净，**工具文档必须逐字节相同**，
   差异只许出现在循环层与步进提示词上；否则「多轮 vs 单轮」里混进了「提示词变了」。

2. **失败分类必须平行建** —— 主路径的 5 态不能套用（见 §3 决策 5）。

3. **⭐ E′ 有可能真的赢，而且不是稻草人。**
   像「哪把椅子离门最近」这类题，主路径必须**盲猜**工具序列（写程序时不知道场景里有哪些椅子），
   而 E′ 可以先 `list_objects` 看一眼再决定。**这是 E′ 的结构性优势。**
   把它当成「证明单轮更优」的陪衬，是自欺。

## 7. 已有的、关于「反馈有用」的实测（口径必须写清）

`logs/agent_runs/` 里 4 道重试题：**最终 4/4 全部救回**。

但那是**错误回灌**（压缩后的失败原因 + `confirmed_ids` 白名单），**不是工具结果回灌**；
而且是「改错」，不是「重新决策」。
⟹ 它说明「给模型一点真实信息、再让它来一次」在本项目上很有效，
**但不能**外推成「E′ 会赢」——这两件事的差别，正是 E′ 要测的东西。
