## 3. 动手前必须定的 5 个接口决策

1. **每轮动作的协议** —— 推荐 JSON 块：`{"tool": ..., "args": {...}}` 或 `{"answer": ...}`。
   不建议直接吐一行 Python：那会让「这一轮算不算 syntax 失败」与主路径的口径混起来。

2. **观察序列化的 token 预算**（⭐ 成本大头）—— `ToolResult.value` 可能是一整张物体表。
   必须定硬预算（例如 ≤400 tok/条）与显式截断声明，否则 E′ 的成本不可预测。

3. **轮次上限** —— `max_tool_turns` 必须是**显式常数**。理由与 `agents/loop.py:27-30` 对
   `max_synthesis_retries` 的说明完全相同：否则「4 轮」与「7 轮」的两次实验在报告里长得一模一样。

4. **答案如何进 `Submission`** —— E′ 的答案由我们构造，但**必须走同一套契约校验**
   （`_to_number` / `_normalize_list`），否则「弃答」判定在两条臂之间会漂移，而弃答率是硬指标。

5. **失败分类** —— 主路径的 `STATUSES` 五态不适合 E′（没有 `static_check` 这一步）。
   E′ 需要自己的枚举，例如 `parse_failed` / `turn_budget_exhausted` / `tool_error_unrecovered`。
   ⚠ `agents/loop.py:71-72` 已写明纪律：**加新状态时必须同时在 metrics 口径里交代它算不算对**，
   否则新状态会静默地既不算对也不算错。

## 4b. 实测收窄（2026-09-21，S0 之后第一次真跑）

### 4b.1 缓存**确实生效**，字段名第一个候选就命中

同一场景同一问题连跑两次（`scripts/run_agent.py --scene living_room --question "哪把椅子离门最近？"`）：

| 量 | 第 1 次 | 第 2 次 |
|---|---|---|
| `prompt_tokens` | 1 934 | 1 934 |
| **`cached_tokens`** | **1 664（86.0%）** | **1 792（92.7%）** |
| `cache_source` | `prompt_tokens_details.cached_tokens` | 同 |
| `completion_tokens` | 509 | 441 |
| `elapsed_s` | 2.607 | 1.969 |
| `est_cost_cny` | 0.010 383 | 0.009 771 |
| `attempts` / `has_reasoning` | 1 / `False` | 1 / `False` |

`usage_keys` 回传 = `['completion_tokens','prompt_cache_hit_tokens','prompt_cache_miss_tokens',
'prompt_tokens','prompt_tokens_details','total_tokens']`。

⚠ **注意首选字段名与备选字段名同时存在**（`details.cached_tokens` 与 `prompt_cache_hit_tokens`），
本实现取前者。**这不是冗余**：`cache_source` 从有值变 `None` 就是「服务商换了字段名、缓存悄悄失效」的告警。

### 4b.2 ⭐ 命中率有**理论天花板**，且零成本可预测

前缀缓存按**前缀**匹配，而 system 块永远在最前面 ⟹

> **命中率天花板 = system 占整条 prompt 的比例**

用 `--dry-run`（**不联网、零成本**）即可读出这两个数：

| 量 | 值 |
|---|---|
| `system_prompt_chars` | 4 016 |
| `tool_docs_chars` | 2 487（占 system **61.9%**） |
| `msg_digest.text_chars`（实测） | 4 299 ⟹ user 侧仅 283 字符 |
| ⟹ system 占整条 prompt | **93.4%** |

**93.4%（天花板）vs 92.7%（实测）** —— 第 1 次的 86.0% 低于天花板，第二次补齐后贴到天花板。
⟹ 结论：**未命中的那部分，恰好就是 user 块（问题 + 场景 hint）**；system 块整体命中。

⭐ 这条的用法：**改完提示词不用发请求**，跑一次 `--dry-run` 就能预判命中率上限。
它把一个"要花钱测"的量变成了"改前就能算"的量。

### 4b.3 E′ 的成本重投影（4 轮，B=1 934 / A=80 / O=320）

逐轮命中结构：第 k 轮的前缀 = 第 k−1 轮的完整 prompt ⟹ 每轮只有**新增的尾巴**（A+O=400）是 miss。

| 口径 | 单轮 | E′ 4 轮 | 倍数 |
|---|---|---|---|
| **账本口径（不套缓存折扣）** | ¥0.010 1 | ¥0.033 3 | **≈3.3×** |
| **含缓存折扣（按 1/10，**未在本项目验证**）** | ¥0.005 2 | ¥0.009 6 | **≈1.8×** |

四种轮数的命中率结构（同一算法）：4 轮 prompt 合计 10 136，命中 8 794 ⟹ **86.8%**。

> ⚠ **区间从 1.2×–4.8× 收窄到 ≈1.8×–3.3×**（4 轮）。**S1 的 5.5× 是上界，不是预期值** ——
> 它按"输入全额计费"算，而实测 87% 的输入命中缓存。
> ⚠ **折扣系数仍然没有被测量**：账本刻意不套折扣（§5 前置 1 的口径不变），
> 所以 1.8× 那一行是**外部假设**，必须以账单为准。**能确证的是 3.3× 这个上界。**

⭐ **成本主导项因此换人了**：扣掉缓存后，**新增的观察（每轮 320 tok，必 miss）** 成了输入侧的主要增量，
而**输出侧只有动作**（80 tok/轮，vs 单轮 475 tok 的完整程序）⟹ **输出侧 E′ 反而更省**（4 轮 320 vs 475）。
⟹ `OBS_BUDGET` 依然是唯一真正有效的成本旋钮，这一点**没变**，但现在有了数字支撑。

### 4b.4 顺带：两个既有成本数字也系统性偏高

1. **单轮 `est_cost_cny` 高估**（未套折扣）——所有历史成本结论都是**上界**。
2. **全量 501 题的 ≈¥18**：跨**题**之间 system 也逐字节相同，且实测**缓存跨运行存活 ≥2 天**
   （本次命中建立在 09-19 那批调用建立的缓存上）⟹ 跑批时除第一题外全程命中，实际应低于 ¥18。

⚠ **测量局限（必须一并写）**：只有 **2 个样本**，且是**同一问题重复**（前缀 100% 相同）；
真实 E′ 的第 2 轮起前缀含模型自己生成的动作，**逐字节可复现性弱于本题** ⟹ 命中率可能低于 86.8%，
但**不会低于"system 块占比"这个地板**（≈88%：system 1 792 / 最长的第 4 轮 prompt 3 134）。

## 5. 前置条件：不做，做了也读不出结论

### 前置 1 —— 账本补缓存命中字段 ✅ **已完成（2026-09-21，S0）**

`llm/adapter.py` 原先的 usage 归一化只取 `prompt_tokens` / `completion_tokens`。
而 `agents/synthesizer.py` 的 `build_messages` 注释明确承诺「工具文档进 system，逐字节稳定 →
能吃服务端前缀缓存」—— 但**账本里没有命中字段，这个承诺无法被证实**。

⟹ 不补这一项，E′ 的真实成本落在 **1.2× 与 4.8× 之间，且我们无法判断在哪**。

**已落地的读法（四个新字段）：**

| 字段 | 位置 | 怎么读 |
|---|---|---|
| `cached_tokens` | 账本 / 每次调用日志 | 命中缓存的输入 token。**`None` = 服务商没报这个字段，不是「报了 0」** |
| `cache_reported_calls` | 账本 | 回报过缓存字段的调用数。**算命中率的分母口径**：为 0 ⟹ 命中率未知 |
| `cache_hit_rate()` | 账本方法 | 没报过时返回 **`None` 而非 `0.0`** —— 「没测到」和「测了没命中」要能分开 |
| `cache_source` / `usage_keys` | 每次调用日志 | 值取自哪个字段名；以及服务商**回传的 usage 顶层键全表** |

`usage_keys` 是**一次真跑就能回答「它到底报不报缓存」**的那一列，不必再猜字段名或翻文档；
`cache_source` 从有值变成 `None`，就是「服务商改了字段名、缓存悄悄失效」的告警信号。

⚠ **口径**：`cost_cny` **刻意不套缓存折扣**（价格表只有两个数，折后价必须由服务商定义，
猜一个系数等于把估计伪装成测量）。当前口径**系统性偏高**，对预算而言是安全方向。

### 前置 2 —— 指标口径先写

E′ 与主路径**能比的只有端到端正确率**（`evaluation/metrics.py` 算的是 Omni3D 四类子指标 + Total）。

「工具选择准确率」在两条臂上**分母不同**（主路径一次选定整条序列／E′ 逐步选），
**不能放进同一张表**。

> ⚠ **此处更正一处此前的说法**：曾讲过「单轮契约让工具选择准确率可观测」，核对后**不准确**。
> 它只出现在三处 —— 注释（`agents/executor.py:101`）、方案文档（§453 与 §1213 的消融表列名）、
> 探针报告（`reports/combination_probe.md:285`）—— 而 **`evaluation/metrics.py` 里没有实现**。
> 原始材料（每次调用与完整 trace）确实在记录里，**但指标本身没写**。
> 这与 §14 那条教训同型：**文档里写了 ≠ 代码里有**。

## 6. 风险与混淆变量

1. **不是纯消融** —— E′ 的 system prompt 与主路径必然不同。要保持干净，**工具文档必须逐字节相同**，
   差异只许出现在循环层与步进提示词上；否则「多轮 vs 单轮」里混进了「提示词变了」。

2. **失败分类必须平行建** —— 主路径的 5 态不能套用（见 §3 决策 5）。

3. **⭐ E′ 有可能真的赢，而且不是稻草人。**
   像「哪把椅子离门最近」这类题，主路径必须**盲猜**工具序列（写程序时不知道场景里有哪些椅子），
   而 E′ 可以先 `list_objects` 看一眼再决定。**这是 E′ 的结构性优势。**
   把它当成「证明单轮更优」的陪衬，是自欺。

`logs/agent_runs/` 里 4 道重试题：**最终 4/4 全部救回**。
