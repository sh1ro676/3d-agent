# `evaluation/` —— 评估口径层

这个目录只回答一个问题：**「一次问答算不算对」到底怎么算。**
它不产生答案、不持有真值 —— 真值属于数据集，答案由 `agents/` 产出。

| 文件 | 职责 |
|---|---|
| `metrics.py` | Omni3D-Bench 的四类子指标 + Total 聚合；口径可被论文自身的数字反推 |
| `tests/` | 口径的回归测试（零 torch、零 GPU、零联网） |

---

## 1. 四条硬约束

1. **`agents/` 不许 import `evaluation/`。** 评估是**量 agent 的器械**，
   器械不能长在被测方身上。依赖方向见方案文档 §13.3(6)，
   `tests/test_agent_layering.py` 用 AST 直接守着这一条。
2. **口径必须能被独立复算。** 子指标定义不自己发明，
   Total 的聚合方式不靠猜 —— 见下面 `derive_total_weights()` 那段。
3. **两个精度口径必须一起报。** 只给一个数，读者一定会误读（§2）。
4. **结果必须自带模型指纹与环境指纹。** §16.2 说得很直白：
   「换模型后的对比无法归因」是这类实验最常见的失败方式。

---

## 2. 两个容易读反的地方（已用测试钉住）

* **无法解析的预测是「记 0 分」，不是「该题被排除」。**
  上游实现的 `num_xxx += 1` 写在 `try` **之前** —— 分母含它。
  如果实现成「排除」，准确率会系统性虚高（极端情况虚高一倍）。
* **`str` 要按答案取值再切成 yes/no 与 multi-choice 两类。**
  只按 `answer_type` 分会把两类合成一类。

本模块因此同时给出两个口径，**引用哪一个必须写清楚**：

    paper-spec —— 逐行对齐上游实现，用于和论文表格对话
    strict     —— 解析失败记 0 分、分母不减，用于「真实能力」叙述

> **权重分布的工程含义**：`numeric_other` 占 **53.9%** 的权重。
> 也就是说这个基准的分数**过半**来自对 float 题的相对误差。
> 任何只针对 count / yes-no 的优化，天花板都不到 15%。

**Total 的聚合方式论文没写，所以这里不猜。** 做法是把它变成一个可证伪的小问题：

    如果 Total 是「按题数加权的 micro 平均」，
    那么用论文自身 7 个方法 × 4 个子指标应当能唯一解出一组题数
    (n_count, n_other, n_yn, n_multi)，且**同时**满足 7 行。

实测（2026-09-17）：同批次 7 行残差 ≤ 0.043 pp，而外部批次的
ViperGPT / VisProg 残差 −6.7 / −7.6 pp ⟹ **规则对，但只对同批次的题数分布成立**。
所以 `verify_total_aggregation()` 只用 `same_run=True` 的行，并把外部行
显式标出来而不是悄悄丢掉。最小二乘反推权重是病态解，已标记 `deprecated`。

## 3. 已知的、会影响结论边界的事实

* **Omni3D-Bench 不提供 GT 相机、也不提供深度或三维框。**
  parquet 只有 6 列：`image_index / image / q_index / question / answer / answer_type`。
  ⟹ 横向米制尺度**仍然**走在「模型自己猜相机」那条不确定路径上，
  不能宣称被基准兜住。这条推翻了此前「基准自带 GT 相机」的记录。
* **实际是 501 题、201 张图**（上游 README 写的是 500）。
  300 行是同一张图的重复出现（平均每图 2.5 问）。
* 上游 `results.txt` 里那个 `Accuracy` 是**逐题字符串相等**，
  float 题几乎不可能命中。它是遗留字段，**不是主指标**
  （本模块仍算它，只为了能和上游产物对上）。
